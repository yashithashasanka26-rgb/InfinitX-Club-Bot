# InfinitX Club

Modular Discord.js v14 bot and guild-settings API. Requires Node.js 20+ and MongoDB.

## Setup

1. Create a Discord application and bot in the [Discord Developer Portal](https://discord.com/developers/applications). Enable **Server Members Intent** and **Message Content Intent** for the moderation and leveling message handlers.
2. Copy `.env.example` to `.env`, fill in the bot token, application credentials, MongoDB URI, and a cryptographically random session secret of at least 32 characters. Set the OAuth redirect URL in the Discord application to the exact `DISCORD_REDIRECT_URI`.
3. Run `npm install`.
4. Run `npm run deploy:commands` to register the global slash commands.
5. Run `npm start` for the bot and `npm run start:dashboard` for the dashboard. Run them as separate processes. The dashboard provides EJS server-selection/settings pages, Discord OAuth routes, and JSON APIs.

Invite the bot with the `bot` and `applications.commands` OAuth scopes and only the permissions its enabled features need. The example permission value is administrator for convenience; replace it with a least-privilege value for deployment.

## Layout

- `src/index.js`: bot startup, MongoDB connection, dynamic command/event loading.
- `src/commands/`: slash commands and per-command execution.
- `src/events/`: Discord event handlers.
- `src/database/models/`: guild configuration, command policy, economy, leveling, warnings, tickets, giveaways, temporary voice rooms, voice sessions, server analytics, starboard posts, suggestions, suggestion logs, and audit logs.
- `src/middleware/`: database-backed guild command policy checks.
- `src/modules/`: reusable moderation, economy, leveling, tickets, music, AI, verification, giveaways, temporary voice, analytics, starboard, suggestions, and custom command services.
- Custom text/embed commands can be managed using the guild-scoped `/api/guilds/:guildId/custom-commands` endpoints.
- `src/dashboard/`: Discord OAuth, secure Express API, and guild configuration routes.
- The dashboard frontend is served from `/` and `/servers/:guildId/settings/:section`. Dedicated Welcome/Leave, command-policy, module, music, ticket/verification panel, and scheduled-message pages use standard form controls rather than requiring everyday JSON edits. Discord OAuth starts at `/auth/discord` and completes at `/auth/discord/callback`; the legacy `/auth/login` and `/auth/callback` routes remain available. Set the Discord application's OAuth redirect URI to exactly match `DISCORD_REDIRECT_URI`.
- Welcome & Leave stores per-guild enabled states, destination channels, optional HTTPS banner/GIF images, and separate welcome/leave embed title, description, color, footer, thumbnail, and date/time display toggles. Templates support `{user}`, `{username}`, `{server}`, `{memberCount}`, `{date}`, and `{time}`; date/time use UTC and can be individually disabled for each embed. Embed footers use the bot avatar as their icon. The bot sends configured embeds on member join/leave when the `welcomeLeave` module and relevant event toggle are enabled. Configure the bot's Server Members intent in the Discord Developer Portal.
- Dashboard server APIs are under `/api/servers`: `GET /api/servers` lists servers where the user is owner, Administrator, or has Manage Server; `GET /api/servers/:guildId` returns guild settings and command permissions; `POST /api/servers/:guildId/update` accepts `{ "prefix": "!", "language": "en", "modules": { "tickets": true }, "settings": { "moderation": { "antiLink": true }, "welcomeLeave": { "welcomeEnabled": true, "welcomeChannelId": "12345678901234567", "welcome": { "title": "Welcome to {server}", "description": "Hello {user}", "color": "#7478ff", "footer": "Enjoy the community", "thumbnailUrl": null } } }, "commandPermissions": [{ "commandName": "warn", "enabled": true }] }`. POST requires a same-origin request, validates IDs, types, URLs, limits, and MongoDB schemas, applies partial updates without resetting omitted sibling fields, and records an audit entry. Command policies include enabled state, cooldown, role requirements, channel allow/deny lists, and use limits. Validation and persistence failures are logged with guild/user context, error name/code, validation paths, and stack details to the dashboard terminal; Mongoose validation/cast failures return actionable 400 responses, while server failures remain generic 500 responses. The earlier `/api/guilds/:guildId/config` endpoints are also retained.
- Guild managers read configuration at `/api/guilds/:guildId/config` and apply validated partial updates with `PATCH` to the same route. This supports module toggles, prefix and locale changes, and all declared moderation, leveling, economy, AI (including greeting auto-reply options), welcome/leave, verification, temporary voice, starboard, suggestions, and ticket settings. `/api/guilds/:guildId/config/schema` lists the supported module and section keys for dashboard clients. Each request revalidates the caller's current Discord guild permissions, validates input and Mongoose schema constraints, stores changes in MongoDB, and records an audit entry.
- Dashboard Discord actions use `POST /api/servers/:guildId/actions` and are processed by the bot through the shared MongoDB `DashboardAction` queue. This supports deploying configured ticket/verification panels and music status/playback controls. The actor must still be in a voice channel to start dashboard playback. Custom embeds can be sent immediately or scheduled using `POST /api/servers/:guildId/scheduled-messages`; list schedules with `GET` on that path and cancel pending messages with `DELETE /api/servers/:guildId/scheduled-messages/:messageId`. Keep both the dashboard and bot processes online for queued actions and scheduled delivery. The bot retries stale scheduled deliveries after worker restarts; ensure it has Send Messages and Embed Links in the target channels.
- Ticket and verification panel pages persist custom embed text, color, image/GIF, footer, button label, and button style. Ticket dropdown categories remain configured under `tickets.categories`. Deploying a verification panel requires an enabled verification configuration and verified role. AI greeting replies are opt-in under the AI module and respond only when a message exactly matches one of the configured `ai.greetingTriggers`; the configured AI provider credentials and rate limits apply.

## Security and operation notes

- The dashboard trusts only the authenticated Discord user and checks their current Discord guild permissions for each guild API request. Configure HTTPS in production and set `DASHBOARD_BASE_URL` and `DISCORD_REDIRECT_URI` to HTTPS URLs.
- OAuth state is single-use and validated. Session cookies are HTTP-only, same-site, secure in production, and persisted in MongoDB. Mutating API requests must come from the configured dashboard origin.
- The bot and dashboard share MongoDB. Keep `SESSION_SECRET`, Discord credentials, and `MONGODB_URI` private; do not commit `.env`.
- Configure `BOT_OWNER_IDS` as comma-separated Discord user IDs to enable `/owner`. This private developer command reports cached server/member totals and runtime health, sends confirmed global announcements to available server system channels, manages user/server blacklist and allowlist entries, and can gracefully stop the bot. Access lists and allowlist-only mode persist in MongoDB; blacklist restrictions take precedence, and bot owners bypass these restrictions. `/owner restart` requires `PROCESS_MANAGER` to be set and relies on an external supervisor (such as systemd, PM2, or Docker) to relaunch the process after graceful shutdown. `/owner shutdown` stops the process without relaunching. Global announcements suppress mentions and require explicit confirmation.
- The bot handles `SIGINT` and `SIGTERM` by stopping background jobs, destroying the Discord client, and closing MongoDB. Uncaught exceptions and unhandled promise rejections are logged and trigger shutdown with a failing exit status. Gateway disconnects, reconnects, resumes, and errors are logged. When starting it programmatically, call the returned client's `shutdown()` method during application shutdown.
- Use a dedicated database user with least-privilege access, MongoDB backups, and a process supervisor. The in-memory spam/cooldown/user-quota trackers are per-process; use a shared limiter such as Redis before running multiple bot replicas.
- AutoMod runs only when the guild enables its module. Configure it through `PATCH /api/guilds/:guildId/config`, for example: `{"modules":{"automod":true},"moderation":{"antiLink":true,"badWords":["blocked phrase"],"messageAction":"timeout","timeoutMinutes":10,"spamThreshold":6,"spamWindowMs":5000,"floodThreshold":4,"floodWindowMs":2000,"duplicateThreshold":4,"raidJoinThreshold":10,"raidWindowMs":10000,"raidAction":"timeout","raidLockdownEnabled":true,"raidLockdownMinutes":10,"nukeProtection":true,"nukeThreshold":3,"nukeWindowMs":10000,"nukeAction":"timeout"}}`. It detects message spam, short-window floods, repeated messages, configured bad words, and optional links, then persists warn/timeout/ban outcomes in the warnings and audit collections. Anti-raid watches join bursts, applies the configured action to members joining during the active incident, and can temporarily deny send permission to `@everyone`; lockdown saves and restores each channel's previous `SendMessages` overwrite and also covers channels created while lockdown is active. Anti-nuke watches destructive audit-log actions when `nukeProtection` is enabled. The bot needs **Manage Channels** for lockdowns, **View Audit Log** for anti-nuke, **Moderate Members** for timeouts, and **Ban Members** for bans, plus sufficient role hierarchy. Configure ban actions carefully to avoid false-positive mass bans. Raid/nuke tracking is process-local, so run one bot worker per guild unless you add distributed coordination.
- This repository is a runnable foundation, not a finished hosted product. It includes XP and coin primitives, command policies, and text/embed custom commands. Nuke action detection is based on audit-log events and does not provide Discord-side rollback of deleted resources.
- Leveling awards randomized XP to eligible messages after a per-user cooldown. Configure `leveling.xpMin`, `xpMax`, `cooldownSeconds`, optional `announceChannelId`, and up to 50 `{ "level": 5, "roleId": "..." }` entries in `leveling.roleRewards`; role rewards are assigned at or above each threshold and existing reward roles are not removed. Use `/level` to check progress and `/leaderboard type:Levels` or `type:XP` to rank members.
- Economy is guild-scoped. `/balance`, `/daily`, `/weekly`, `/work`, `/pay`, `/shop view`, `/shop buy`, and `/inventory` operate on Mongoose-backed accounts and an expiring transaction ledger. Configure reward amounts, work bounds/cooldown, and up to 25 unique `{ "itemId": "badge", "name": "Badge", "description": "Example", "price": 250 }` shop entries under `economy`. `/pay` uses MongoDB transactions and therefore requires MongoDB Atlas or another replica-set deployment. `/leaderboard type:Coins` ranks coin balances.
- Ticket panels are posted with `/ticket-panel` after enabling the tickets module. Configure up to 25 dropdown categories with `tickets.categories`, each with a unique `key`, display `label`, optional `description`, and optional category/support role IDs (otherwise the guild-wide ticket settings are used). Tickets get private channels, one active ticket per user, owner/support/manager close controls, transcripts retained in MongoDB for 30 days, optional transcript log-channel delivery, and an inactivity auto-close sweep using the configured `autoCloseHours`. `/ticket` provides close, reopen, claim, add-user, remove-user, and transcript subcommands. Dashboard managers can list records at `/api/guilds/:guildId/tickets`, see aggregate counters at `/api/guilds/:guildId/tickets/stats`, and retrieve an unexpired transcript by ticket record ID at `/api/guilds/:guildId/tickets/:ticketId/transcript`. The bot needs Manage Channels and the ticket category, support role, and log channel should be configured in the dashboard.
- Music is implemented with `@discordjs/voice`, YouTube/SoundCloud resolution via `play-dl`, bundled FFmpeg transcoding, and the `opusscript` codec fallback. Enable `modules.music` for the server in the dashboard, then register commands with `npm run deploy:commands`. Available commands are `/play`, `/pause`, `/resume`, `/skip`, `/stop`, `/queue`, `/volume` (0–200%), `/loop` (off/track/queue), `/shuffle`, and `/nowplaying`. `/play` accepts YouTube and SoundCloud track URLs or a YouTube search term; playlist URLs are not supported. The bot needs **Connect** and **Speak** in the voice channel. Playback sessions are per guild, queues are limited to 100 upcoming tracks, and an idle player disconnects after one minute. Streaming source availability and platform policies may change, so use this feature only for content you are authorized to play.
- AI features use the OpenAI API by default or Google Gemini through the provider adapter. Set `AI_PROVIDER=openai` or `gemini`, `AI_API_KEY`, and optionally `AI_MODEL` in the bot's private environment. To fail over on temporary provider errors or rate limits, configure `AI_FALLBACK_PROVIDER=gemini` (or `openai`) and `AI_FALLBACK_API_KEY`; separate `OPENAI_API_KEY`/`GEMINI_API_KEY` environment keys are also recognized. Never put provider keys in the dashboard or commit them. Enable `modules.ai` per server; opt into public bot-mention replies (`ai.mentionResponses`) or exact greeting auto-replies in the dashboard. Register commands with `npm run deploy:commands`: `/ai chat`, `/ai ticket-summary`, `/ai ticket-reply`, `/ai moderate`, `/ai embed`, and `/ai announcement`. Ticket tools require the configured support role, Manage Channels, or Manage Messages in the ticket; generated replies, moderation analyses, embeds, and announcements are private previews and require human review. AI requests are rate-limited per member and server. Text submitted to AI commands or bot messages is sent to the configured external AI provider; inform members and follow your server's privacy policy. AI moderation is advisory only and never automatically punishes members.
- Custom commands are stored in MongoDB and managed by server members with **Manage Server**. Enable `modules.customCommands` in the dashboard and configure a short server prefix (default `!`); `/custom-command set` creates or updates a trigger name with optional text, embed JSON, and HTTPS link buttons, `/custom-command list` shows configured triggers, and `/custom-command delete` removes one. Members invoke them as `<prefix><name>`; matching is case-insensitive and additional trailing text is ignored. The dashboard API also supports `GET`, `PUT`, and `DELETE /api/guilds/:guildId/custom-commands/:commandName`. Responses suppress mentions by default. `/embed-builder` opens an interactive modal for title, description, up to 25 fields, color, footer, and up to five HTTPS link buttons, then sends the preview to the invoking channel. Both management commands require Manage Server and the custom-commands module enabled. Buttons are safe link buttons only; they do not run arbitrary callbacks.
- Moderation includes `/ban`, `/kick`, `/timeout`, `/warn`, `/purge`, `/lock`, `/unlock`, and `/slowmode`; commands enforce Discord permissions, target/self/role-hierarchy checks where applicable, and record actions in MongoDB. Configure `moderation.logChannelId` to a text channel ID using `PATCH /api/guilds/:guildId/config` (for example `{"moderation":{"logChannelId":"123456789012345678"}}`). The bot posts message edit/delete, member join/leave, voice state, configured moderation command, and Discord audit-log moderation events there. Give the bot View Channel, Send Messages, and Embed Links in that channel; enable the Guild Moderation intent (already configured in the client) to receive audit-log events. Deleted message logging can only include content available to the bot at event time; bulk purge ignores messages older than Discord's 14-day bulk-delete limit and logs the actual deletion count.
- Verification uses `/verification setup role:<role> channel:<channel>` after enabling `modules.verification` in the dashboard. The bot posts a button panel and gives the configured role after a member solves a short arithmetic challenge; `/verification disable` stops new challenges. Configure channel/role permissions separately so unverified members cannot see restricted server channels, and grant the bot **Manage Roles** with its highest role above the verified role. Challenges expire after five minutes, are one-use, and are held in process memory, so members must restart verification after a bot restart. This lightweight challenge is not a substitute for a dedicated CAPTCHA or other anti-bot controls.
- Giveaways use `/giveaway start prize:<text> duration:<10s–30d> [winners] [required-role] [minimum-level]`, then `/giveaway end message-id:<id>` or `/giveaway reroll message-id:<id>`. Enable `modules.giveaways` in the dashboard first; entrants are persisted and deduplicated in MongoDB, eligibility is checked when entering, and expired giveaways are completed by a recoverable scheduler. Rerolls exclude all previously selected winners. The bot needs **View Channel**, **Send Messages**, and **Embed Links** in the announcement channel; giveaway management requires **Manage Server**.
- Temporary voice rooms are configured with `/tempvoice setup join-channel:<voice-channel> [category:<category>]`; setup enables the module and stores its configuration. Joining the selected voice channel creates a private voice room and its private text-control channel, then moves the member into the room. The panel provides Rename, Lock, Unlock, Hide, User Limit, Invite, Kick, and Transfer Ownership controls; kick and ownership transfer target a member currently in the room, and rooms (including their control channels) are deleted when empty. The bot needs **Manage Channels** and **Move Members**. Active room ownership is persisted; empty or stale rooms are reconciled at startup.
- Server Analytics is enabled by setting `modules.analytics` to `true` in `PATCH /api/guilds/:guildId/config`. `/analytics period:<daily|weekly|monthly>` reports member joins/leaves and net growth, non-bot message counts, voice sessions, and voice-connected duration. Aggregates are stored by UTC calendar day; weekly covers the latest seven UTC dates and monthly the latest 30. Voice durations are split at UTC midnight. A connected session is restarted from bot startup after a restart (offline time is excluded; an unfinished portion from before restart is not counted). Analytics are collected only while the module is enabled.
- Starboard is configured with `/starboard setup channel:<channel> threshold:<count> [emoji]`; the default emoji is ⭐. The bot posts or updates a source-message embed once the configured reaction count is reached, removes it if reactions fall below threshold, and removes the starboard post if the source message is deleted. `/starboard disable` stops processing. The bot needs **View Channel**, **Send Messages**, and **Embed Links** in the starboard channel and visibility of reactions in source channels. The client uses the Guild Message Reactions intent and Reaction partials so uncached message reactions can be fetched.
- Suggestions are configured with `/suggestion setup channel:<channel> [log-channel:<channel>]`. Members submit through `/suggestion submit`, then vote with upvote/downvote buttons; clicking the same vote again removes it, and switching buttons changes vote direction. Managers with **Manage Messages** can run `/suggestion approve message-id:<id> [reason]` or `/suggestion reject message-id:<id> [reason]`. Suggestion posts, vote totals, decisions, and action logs are stored in MongoDB; the optional log channel receives submission and decision notices. Vote and decision buttons are disabled after a decision.
- A richer custom dashboard experience beyond the included server selector/settings form, automated deployment, distributed rate limiting, and production observability are not included. Review permissions, privacy/retention policy, and feature-specific failure handling before public deployment.
